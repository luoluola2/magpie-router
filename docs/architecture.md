# 架构

## 控制闭环

`Observation → Evaluation → Proposal → Approval → Apply → Verification → Rollback`

1. **Observation**：通过 `magpie` CLI 读取供应商、模型、Agent 和路由组；需要时读取用量证据与本地 `/v1/models` 元数据。
2. **Evaluation**：结合工作负载与策略识别不可用成员、候选集中度和能力缺口；单次额度与延迟读数只是随时间变化的证据。
3. **Proposal**：`Change Set` 是一份路由规范与实时配置间的完整差异集合，包含每个受影响组的基线、目标、理由和回滚信息。
4. **Approval**：应用前确认完整差异及写入范围。只有本次明确批准、且仍出现在 `route diff` 中的组可以写入。
5. **Apply**：重新观测并核对基线，按组依赖顺序应用差异；基线漂移、无效成员或无法验证时停止。
6. **Verification**：回读实际配置，运行 `route diff` 与 `audit`，确认目标和拓扑。
7. **Rollback**：失败组尝试恢复本组基线并记录结果；已成功组不自动回滚。整轮快照保存在本地状态目录。

## 模块

安装入口为 `magpie-router`，也可在本地开发时运行 `python -m magpie_router`。

业务路由采用 Work → 任务入口 → 资源池 → 具体模型四层结构；Jev 原生分类器是辅助控制引用，SOTA 为手动入口。分层策略见 `config/routing-overview.md`。

| 模块 | 职责 |
| --- | --- |
| `paths` | 提供策略、数据库、快照、证据和工作记录的唯一默认路径来源。 |
| `model` | 表示路由组和规则，解析 Magpie CLI 输出并采集只读视图。 |
| `spec` | 加载并验证唯一的 v4 路由规范，计算依赖顺序和暴露模型。 |
| `compare` | 比较实时配置与规范，并检查层级引用和可验证问题。 |
| `apply` | 按组应用完整规范差异，记录应用结果并在失败时恢复基线。 |
| `store` | 维护本地 SQLite 配置镜像和逐组应用日志。 |
| `magpie` | 定位 CLI、传递参数并保留退出码与诊断输出。 |
| `contexts` | 从只读网关元数据读取有效公布容量，不发送推理请求。 |
| `cli` | 暴露只读盘点、审计、数据库同步及 route diff/apply 命令。 |

CLI 文本是当前 Magpie 版本的观察接口，不是稳定的跨版本序列化协议。解析失败必须显式报错；未来有结构化接口时，优先在 `model` 或 `magpie` 边界替换。

## 本地状态

`paths` 集中定义所有默认路径：期望策略在 `config/`；SQLite 镜像位于 `state/db/`；回滚快照、脱敏观测和工作记录分别位于 `state/snapshots/`、`state/evidence/`、`state/work/`。这些本机数据不进入 Git。SQLite 保存当前组、成员、规则、观测、期望规范和逐组应用记录；字段见 `docs/database.md`。

## 当前边界

项目通过 Magpie CLI 操作路由，不复制账户池、密钥管理、请求代理或故障转移实现。它不根据供应商名称推断模型能力、价格或上下文，也不通过测试任意模型来验证只读盘点。主动探测会消耗额度，必须另行授权。

数据库只镜像路由配置与回滚证据，不保存用量、配额、会话或自动评分。项目当前提供显式评估与应用，不执行定时优化或自动写入。
