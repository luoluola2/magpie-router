# 架构

## 控制闭环

`Observation → Evaluation → Proposal → Approval → Apply → Verification → Rollback`

1. **Observation**：通过 `magpie` CLI 读取供应商、模型、Agent、路由组和必要的用量证据。
2. **Evaluation**：结合工作负载与策略识别不可用成员、候选集中度和能力缺口；额度只是其中一个随时间变化的输入。
3. **Proposal**：生成单个路由组的 Change Set，记录当前成员、期望成员和理由。
4. **Approval**：人确认范围后才允许写入。Agent 可准备和解释计划，不能借优化之名扩大权限。
5. **Apply**：重新读取目标组并核对完整基线，避免覆盖期间的人为修改。
6. **Verification**：读取实际配置，确认成员与顺序完全符合计划。
7. **Rollback**：根据计划恢复原成员；回滚也必须重新核对基线，不能盲目覆盖后续变更。

## 模块

当前实现保持一个小接口：`python -m magpie_router`。

- **Magpie adapter**：定位 CLI、执行参数数组、保留退出码与诊断输出。供应商凭据永不进入计划。
- **Route model**：从组详情解析成员、顺序和可用性，并比较基线。
- **Planner**：为单组顺序调整生成计划及反向计划。
- **Auditor**：报告未暴露成员、空路由链等确定性问题，不假装推断模型质量。

CLI 文本是当前 magpie 版本的观察接口，不是稳定的跨版本序列化协议。解析失败应显式报错；未来有结构化接口时，优先在 adapter 内替换，不把格式传播到策略层。

## 实施阶段

1. **当前：受控单组变更**。只读盘点、审计、计划、基线保护、应用与验证。
2. **证据积累**。在 `.local/` 保存脱敏、带时间戳的决策摘要，按工作负载比较成功、延迟、成本和配额节奏。
3. **建议自动化**。定时生成提案和回归报告，默认仍需批准；支持明确的长期 Policy。
4. **有限自动应用**。只对可逆、低风险和经过历史验证的变更开放，保留全局暂停、漂移保护和审计记录。

## 明确不做

- 不复制 magpie 的账户池、密钥管理、请求代理和故障转移实现。
- 不根据供应商名称假定模型能力、价格或上下文大小。
- 不通过测试任意模型来“验证”只读盘点；主动探测会消耗额度，必须单独授权。
- 不在没有跨时间证据时引入自动评分、数据库或常驻调度服务。
