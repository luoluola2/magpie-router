# Jev 接入与 v4 迁移状态

2026-11-10，用户同意按 Magpie 原生方式接入 Jev。业务路由仍保持四层；分类器是辅助控制引用，允许直接指向决策模型，不强制经过普通任务组和资源池。

当前 `group/entry-work` 的分类器为 `typesafe/jev-latest`。原有成员与规则未因这次分类器变更而调整，原始组详情保存在本机 `state/evidence/before-jev-entry-work.txt`。恢复时应先读取当前 Work 状态，再按需要将分类器改回 `group/task-classify`，不能盲目覆盖其他修改。

合成请求分别直接调用 Jev 和经一个临时决策模型组调用 Jev，均得到预期分类；两个请求分别消耗 313 和 323 个输入 token。临时组已删除。这只证明分类接口和决策组可响应，不证明 Work 的意图规则命中质量或真实业务效果。

Magpie 0.1.3492 拒绝将包含 Jev 的决策组作为另一组的普通成员；它可以被指定为分类器。因此原计划的 `task-classify → pool-classify → Jev` 不可作为业务成员链实施。Jev 当前标称上下文 32k，分类组公布更大容量不能据此增加其实际容量。

v4 的业务入口和普通任务意图规则已迁移，配置见 `config/routing.json`。Magpie 规则命中后仍会回退到入口中的其他成员，因此无法同时实现自动强化和强化任务绝不降级。2026-11-11 用户重新确定边界为「自动强化 + 允许降级」：强化入口已加入 Work 成员并恢复意图规则，失败时显式回退 `task-implement`；取舍见 `docs/adr/0002-strong-routing-degradation-boundary.md`。2026-11-10 已从 Codex 生成文件回读五个角色的新任务组绑定；新会话加载和真实任务的分类效果尚未验证。

使用五条合成文本直接请求 Jev，在通用问候、评审、架构、实现及视觉五种候选中均得到预期选择；这是简短样例，不是 Work 网关端到端调用，也不能证明真实任务的分类质量或历史上下文传递。
